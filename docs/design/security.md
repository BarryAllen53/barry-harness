# Barry Harness: Security Design

Status: design target. Release 0.1.0 is a chat client without tools, so most of this document is planned. Section 9 lists the secret handling that ships today, and `implementation-status.md` maps the rest.

Scope: a local-first desktop agent that sends the user's code and prompts to third-party model APIs and executes model-chosen tools (file edits, shell, MCP servers, network fetches, image generation) on the user's Windows 11 machine with the user's privileges. The central fact: the model is an untrusted, manipulable component whose output is data that drives powerful actions.

## 1. Assets, actors, trust boundaries

Assets (ranked): (1) user files and credentials reachable by the user account (SSH keys, browser profiles, cloud CLI tokens, `.env` files), (2) provider API keys (spend and abuse), (3) source code and prompts (confidentiality towards third parties), (4) integrity of the workspace, (5) the harness's own configuration (permission rules, hooks, MCP definitions), (6) the user's attention (approval fatigue is an attack surface).

Actors: the user (trusted); the model (untrusted output); content the model reads (web pages, files in cloned repos, tool results, MCP responses: untrusted, may contain injected instructions); MCP servers (third-party code, semi-trusted after explicit user trust); provider APIs (trusted for transport, not for authorization); other local processes and users on the machine; a compromised webview (XSS through rendered model text).

Trust boundaries:

1. Webview <-> Rust backend (ipc.md): backend authoritative.
2. Agent <-> tools: every tool call passes policy.
3. Tools <-> OS: sandbox and path policy.
4. Harness <-> MCP server processes: separate process, trust-gated, secrets scoped.
5. Harness <-> internet: only the backend egresses; allowlisted purposes.
6. Harness <-> keyring/disk: secrets in keyring only.

## 2. Threat model

| ID | Threat | Vector | Impact | Primary mitigations |
|---|---|---|---|---|
| T1 | Direct prompt injection | user pastes hostile text | tool misuse | policy independent of model; user is the one pasting |
| T2 | Indirect prompt injection | instructions inside files, web pages, MCP output, repo docs, issue text, tool results | model reads secrets and exfiltrates, writes backdoors, runs commands | taint tracking, no autonomous network after untrusted read in Auto mode, approvals, egress control, content framing, hard-deny list |
| T3 | Tool abuse / confused deputy | model calls shell/write with attacker-chosen args | arbitrary code execution as user, destructive writes | capability classification, permission modes, sandbox, path policy, checkpoints |
| T4 | Path escape | `..`, absolute paths, junctions/symlinks, short names, ADS, UNC, device names | read/write outside project | canonical path resolution with reparse-point checks (section 6.2) |
| T5 | Secret leakage to provider | `.env`, key files read into context | secrets stored at provider/logs | sensitive-path read denial, secret scanner on tool output, redaction before context |
| T6 | Secret leakage locally | keys in logs, DB, events, crash dumps, exports | credential theft | keyring storage, sensitive headers, key redaction in error messages; planned: `SecretString`, a log redaction layer, canary tests |
| T7 | Exfiltration channel | web_fetch URLs with data in query, image URLs rendered in UI, MCP tools with network, shell `curl` | data leaves machine | egress policy, no remote images in UI, URL policy, taint gating |
| T8 | SSRF via web_fetch | model fetches `http://169.254.169.254`, localhost admin ports, `file:` | internal service access | scheme allowlist, resolved-IP blocklist with DNS pinning, redirect re-validation |
| T9 | Malicious MCP server | tool descriptions with injected instructions, rug-pull updates, stdio server running arbitrary code | RCE, injection | explicit trust with fingerprint, schema/description pinning, scoped env, Job Object limits, annotation hints untrusted |
| T10 | Config tampering | model/tool writes `.barry/` settings, hooks, or MCP config to escalate | persistent privilege escalation | harness config paths in the protected-path list; writes always require user approval and are never auto-allowed |
| T11 | Webview compromise | XSS from markdown/HTML in model output | calls to IPC | no raw HTML, CSP, command whitelist, approvals enforced in backend, no network in webview |
| T12 | Approval fatigue / spoofing | flood of prompts, misleading summaries | user approves harmful action | summaries generated by backend from structured args (not model text), diffs, rate-limit prompts, "dangerous" visual tier |
| T13 | Resource exhaustion | infinite loops, fork bombs, huge outputs, giant files | DoS, cost blowup | Job Object limits, timeouts, output caps, turn budgets (steps, tokens, cost) |
| T14 | Supply chain | crates, frontend deps, updater | compromised build | `cargo-deny` advisories, bans, licenses and sources in CI, lockfile committed, actions pinned to commit SHAs, release zip published with a SHA-256 checksum; planned: `cargo-audit`, code-signed releases |
| T15 | Cost abuse | agent loops image generation or long contexts | API bill | per-session and per-day cost ceilings, media confirm, step limits |
| T16 | Local other-user/process attack | read DB/blobs, tamper config | data theft | per-user `%LOCALAPPDATA%` ACLs (inherits user-only), no network listeners (no localhost server at all), named-pipe none |
| T17 | Replay/enumeration of IPC | rogue local process calling Tauri | none by design: Tauri IPC is in-process to its webview; no localhost port is opened (production uses custom protocol, dev server only in debug builds) |

Non-goals (stated honestly): defending against a fully compromised OS account, a malicious provider, or a determined adversary with kernel access; OS-level network isolation for shell in v1 (see section 7); preventing the model from producing harmful text.

## 3. Prompt injection strategy

Prompt injection cannot be solved by prompting; the design assumes it will succeed against the model and constrains what a hijacked model can do.

1. **Authority never comes from model text.** Permission decisions use structured capabilities derived from validated tool inputs, never from the model's stated intent or a "the user said it's okay" message.
2. **Taint tracking (provenance).** Every tool result carries a taint label: `Trusted` (harness-produced, user-typed) or `Untrusted` (web, MCP, files outside harness-created set, shell output). The agent maintains a per-turn `session_tainted: bool` set when untrusted content enters context. Effects while tainted:
   - In `Auto` mode: capabilities `Network`, `Exec`, `FsWriteOutside`, `McpCall` (non read-only hint), `MediaGenerate` and any write to protected paths are downgraded from allow to ask. (Reads and in-workspace edits stay auto.) This blocks the classic "read hostile page -> run curl with secrets" chain without UI churn for pure editing.
   - Approval cards show a "context contains untrusted content from: <sources>" line.
   - Taint clears only at a new user message that the user typed (not on compaction).
3. **Content framing.** Untrusted tool output is wrapped in a stable envelope in the tool result (`<tool_output source="web_fetch" trust="untrusted">...</tool_output>`) and the system prompt instructs the model that such content is data. This is defense in depth, not a boundary. The envelope is part of the stored bytes (cache-stable).
4. **Sensitive data never auto-enters context.** `read_file` and `grep` refuse (policy `SensitivePath`) a deny-by-default list unless the user explicitly approves per path: `.env*`, `*.pem`, `*.key`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `.ssh\`, `.aws\`, `.azure\`, `.config\gcloud`, `.kube\config`, `.npmrc`, `.pypirc`, `.git-credentials`, `.netrc`, browser profile dirs, `NTUSER.DAT`, Windows credential stores, and the harness data dir itself. The list is configurable (add-only for managed policy).
5. **Secret scanner on outbound context.** Before tool output enters the request, a fast regex+entropy scanner (patterns for `sk-ant-`, `sk-`, AWS keys, GitHub tokens, private key PEM blocks, JWTs, connection strings) redacts matches as `[REDACTED:kind]` and records an audit entry; for `read_file` of a non-denied file containing secrets the user is warned once per file with option to allow. The scanner also guards user-pasted text with a warning (not silent redaction).
6. **No remote rendering exfil.** The UI never loads remote images/URLs from model output (ipc.md section 4.3), eliminating markdown-image exfiltration.
7. **Tool descriptions are pinned.** MCP tool name/description/schema are hashed at trust time; a change disables the server until re-trusted (rug-pull defense). Descriptions are length-capped (2 KiB) and scanned for instruction-like injection markers; matches only produce a warning, since heuristics are bypassable.
8. **System prompt isolation.** Project instruction files (AGENTS-style) are loaded as `Project` stability system content; they are untrusted if the project is untrusted. First open of a project asks "Trust this folder?"; untrusted folders load no hooks, no project MCP config, no project instruction files, and `Auto` is unavailable.

## 4. Permission modes

Modes are per session, changeable at any time (the change is a persisted, audited event). Capabilities are those in contracts.md section 4.

| Mode | Reads in workspace | Edits in workspace | Exec (shell) | Network | MCP | Outside workspace | Intended use |
|---|---|---|---|---|---|---|---|
| `Plan` | allow | deny (tools hidden from the model; only a `plan` output tool) | deny | deny (except provider) | read-only hint tools ask | deny | design and exploration |
| `Ask` (default) | allow | ask | ask | ask | ask | ask | normal |
| `AcceptEdits` | allow | allow (non-protected paths) | ask unless in allow rules or read-only-classified | ask | ask | ask | supervised coding |
| `Auto` | allow | allow | allow if matched by classifier "safe" or allow rule, else ask | ask for new hosts, allow allowlisted | allow trusted read-only, else ask | ask | trusted projects, long tasks |

There is no "bypass all" mode. `Auto` still enforces: hard-deny list, protected paths, sandbox, taint downgrades, cost ceilings, step limits. Enabling `Auto` requires the project to be trusted and an explicit confirm (audited); it cannot be set by config file alone, only through the UI/CLI confirmation, and a managed policy can forbid it.

### 4.1 Evaluation order

```
verdict(capabilities, ctx):
  1. hard-deny list matches              -> Deny (not overridable; reason HardDeny)
  2. managed-policy deny rules           -> Deny
  3. user/project/session deny rules     -> Deny
  4. PreToolUse hooks (section 5)         -> may Deny, may force Ask, may attach notes; a hook cannot grant Allow beyond the mode
  5. protected-path writes               -> Ask always (even Auto, even with allow rules)
  6. mode defaults + taint downgrades    -> Allow | Ask
  7. allow rules (session, project, user, managed)  -> can upgrade Ask to Allow unless step 5 or taint-sensitive
  8. otherwise                           -> Ask
```

Multiple capabilities in one call: the most restrictive wins (Deny > Ask > Allow). Deny rules beat allow rules regardless of scope specificity; among same-decision rules the narrowest scope is reported. Rule matchers are structured, never free-text regex over model output: `Fs { glob }` (matched against the canonical workspace-relative path), `Exec { program, arg_prefix }` (matched against parsed argv for direct exec; for shell strings only exact normalized command-line match, never prefix/wildcard, because shell parsing is not a security boundary), `Network { host }` (exact or `*.suffix`), `Mcp { server, tool }`.

### 4.2 Hard-deny list (always, all modes)

Writing or deleting: harness data dir, `.git\hooks\*`, `.git\config` (except through a dedicated git tool, not in v1), harness config files and `.barry\` hook/MCP configuration, OS directories (`%SystemRoot%`, `Program Files*`), startup folders and Run keys, `%USERPROFILE%` dotfile credential stores listed in section 3.4, and roots of drives. Exec patterns outright refused: `format`, `diskpart`, `reg add/delete HKLM`, `bcdedit`, `vssadmin delete`, `cipher /w`, `schtasks /create`, `New-Service`/`sc create`, `Set-ExecutionPolicy`, `Invoke-Expression` of downloaded content (`iex (iwr ...)`, `irm | iex`), `Start-Process -Verb RunAs`, `net user`, `netsh advfirewall`, `Disable-WindowsDefender*`/`Set-MpPreference`, and commands with `-EncodedCommand` (opaque payloads). These are matched on a tokenized PowerShell AST via `System.Management.Automation.Language.Parser` run in a helper invocation (see 7.3) with a conservative fallback: if parsing fails the command is `Ask`. The list is a guardrail against accidents and injection, not a complete security boundary, and is documented as such.

### 4.3 Approval UX requirements

- Summary text is generated by the backend from structured arguments: tool, capability list, exact command or file path, a diff for writes (with limit and "view full"), and risk tier (`Low` read, `Medium` workspace write, `High` exec/network, `Critical` outside workspace/protected path/destructive pattern). Model-written description strings may be shown only in a clearly separate "model says" field.
- Grants: `Once`, `Session`, `Project` (the latter persisted in `permission_grants`, audited; offered only for narrow rules like "this exact command" or "this program with these args prefix" or "write to this directory glob", never "all exec").
- Anti-fatigue: identical ask within a turn is deduplicated; more than 10 prompts in a turn raises "consider changing mode or adding a rule" and does not auto-approve.
- Denial feedback is returned to the model as a tool error (`PolicyDenied`) with optional user text.
- Approvals are bound to the exact call (`ApprovalId` + `ToolCallId` + arguments hash); a changed argument requires a new approval (no time-of-check/time-of-use mutation).

## 5. Hooks

Hooks let the user add deterministic policy and automation without trusting the model. They are declarative, user-defined, and run by the backend (never by the frontend or the model).

Events: `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `SessionStart`, `TurnEnd`, `PermissionRequest`.

Definition (stored in user config and, if the project is trusted, in project config; project hooks are shown for review on first load and re-reviewed on change, via content hash):

```toml
[[hook]]
event = "PreToolUse"
match = { tool = "shell" }
command = ["pwsh", "-NoProfile", "-File", "C:\\Users\\me\\hooks\\check.ps1"]
timeout_ms = 5000
on_failure = "deny"
```

Contract:

- Input: JSON on stdin (`session`, `turn`, `tool`, `arguments`, `capabilities`, `cwd`, `mode`), no secrets.
- Output: exit code 0 and optional JSON stdout `{ "decision": "deny"|"ask"|"allow_noop", "reason": "...", "additional_context": "..." }`. Exit code 2 = deny with stderr as reason. Any other nonzero exit, timeout, or invalid JSON follows `on_failure` (default `deny` for `PreToolUse`, `ignore` for `PostToolUse`).
- Hooks run via the same sandbox profile as the shell tool minus network, with env scrubbed (section 7), in the project root, with a hard timeout (default 5 s, max 60 s) and 64 KiB stdout cap.
- A hook may tighten (deny, ask) but never loosen: `allow_noop` means "no objection". Only the user's rules and mode can allow. This stops a hijacked repo hook from silently approving things.
- `additional_context` from hooks is treated as untrusted-tainted when the hook is project-defined and trusted when user-defined; capped at 4 KiB.
- Hook configuration files are protected paths (write always asks and the model is told it cannot create or modify hooks; hooks changes are made by the user in the UI or by editing the files themselves).
- Hook execution is audited (hook id, duration, decision).

## 6. File and path security

### 6.1 Workspace model

`WorkspaceRoot` is a canonicalized project directory, opened as a directory handle at session start. All file tools accept a path string, resolve it through `WorkspaceRoot::resolve(input) -> WorkspacePath | Outside(PathBuf)`; there is no other way to open files in tool code (a clippy `disallowed_methods` lint bans `std::fs::*`/`tokio::fs::*` in `bh-tools` outside the `workspace` module, enforced in CI).

### 6.2 Windows path rules

1. Reject on input: embedded NUL, control characters, trailing dot/space segments, alternate data streams (any `:` after the drive letter), device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9`, with or without extensions), `\\.\` and `\\?\GLOBALROOT` namespaces, UNC paths (`\\server\share`) unless the project root itself is UNC (not supported in v1: rejected at `project_add`).
2. Normalize: join with root, resolve `.`/`..` lexically, expand 8.3 short names via `GetLongPathNameW`, then canonicalize with `GetFinalPathNameByHandleW` on an opened handle (for existing paths) or on the deepest existing ancestor (for creation), strip `\\?\`, and compare case-insensitively (Unicode simple case folding; NTFS is case-insensitive by default, per-directory case-sensitivity is honoured by comparing on the folded form conservatively).
3. Containment check on the final canonical path: it must start with the canonical root plus separator.
4. Reparse points: any junction, symlink or mount point encountered along the path whose target is outside the root causes `Outside` classification (so it needs approval, and writes through it are denied in `Auto`). Creating symlinks/junctions via file tools is not offered.
5. TOCTOU: file operations open with the handle-based flow: open parent directory handle -> open the target with `FILE_FLAG_OPEN_REPARSE_POINT` where relevant -> verify final path via `GetFinalPathNameByHandleW` on the opened handle again -> operate on that handle. Writes use create-temp-in-same-directory then `ReplaceFileW`/atomic rename, preserving ACLs, so a crash never leaves a half-written file.
6. Case: `Foo.txt` vs `foo.txt` considered same path for rules and checkpoints.
7. Read limits: 2 MiB per `read_file` call (line ranges supported), binary detection (NUL in first 8 KiB) returns a stub, not content. Write limits: 5 MiB per call.

### 6.3 Protected paths (writes always ask; deletes always ask)

Inside workspace: `.git\` (all), `.barry\`, `.github\workflows\`, `.vscode\tasks.json`, `.vscode\settings.json`, `.idea\`, `*.ps1`/`*.bat`/`*.cmd`/`*.lnk` in startup-like locations, `Cargo.toml`/`build.rs`/`.cargo\config.toml` (build-time code execution vectors) are flagged `Medium+` with an explicit "executes at build time" note but follow normal mode; the list is configurable. Hard minimum: `.git\hooks`, `.git\config`, `.barry\`.

## 7. Sandbox v1 on Windows

### 7.1 Honest scope

Windows has no seccomp/bubblewrap equivalent that is both strong and dependency-free for arbitrary child processes launched by an unprivileged desktop app. v1 provides process containment and resource limits, not a filesystem or network jail for shell commands:

| Property | v1 enforcement | Notes |
|---|---|---|
| Kill-tree on cancel/exit/crash | Yes: Job Object `KILL_ON_JOB_CLOSE` | the harness never leaks child processes |
| CPU/memory/process-count limits | Yes: Job Object (`ProcessMemoryLimit` 4 GiB default, `ActiveProcessLimit` 64, `PerProcessUserTimeLimit` optional) | stops fork bombs and runaway memory |
| UI restrictions | Yes: Job `UILIMIT` (no desktop switch, no clipboard, no global atoms, no `ExitWindows`) | |
| Privilege reduction | Yes: `CreateRestrictedToken` with `DISABLE_MAX_PRIVILEGE`, administrators group set deny-only; process runs at Low or Medium-Low integrity where compatible | If the user is an admin, UAC elevation is not inherited; children can never elevate silently |
| Environment scrubbing | Yes: allowlist env (`PATH`, `SystemRoot`, `TEMP` (redirected), `USERPROFILE` unchanged, `HOME`, locale vars, `COMSPEC`); strips `*_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, cloud and CI variables, `ANTHROPIC_*`, `OPENAI_*` | |
| Working directory | Yes: set to project root (or validated subdirectory) | not a jail |
| Output caps and timeouts | Yes: stdout+stderr 1 MiB captured (rest dropped with marker), default timeout 120 s, max 600 s per policy | |
| File system confinement | No in v1 for shell. In-process file tools are confined by path policy; shell can touch anything the user can | mitigated by approvals, hard-deny patterns, checkpoints for tracked file tools only |
| Network confinement | No at OS level in v1 for shell | mitigated by classification (`Exec` always approved unless safe-classified), egress capability prompts for known network programs, taint downgrade |

This table appears in the UI's security page so users do not assume a stronger guarantee. Shell commands in `Auto` run only when classified safe (section 7.3) or matched by an explicit user allow rule; anything else asks.

### 7.2 Launch procedure (`bh-sandbox`)

1. Build a restricted token from the process token (`CreateRestrictedToken`, `DISABLE_MAX_PRIVILEGE | LUA_TOKEN` where it does not break common toolchains; compatibility flag falls back to `DISABLE_MAX_PRIVILEGE` only, recorded in the audit log).
2. Create a Job Object with the limits above; set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` off so children cannot escape.
3. `CreateProcessAsUserW` (or `CreateProcessW` with the restricted token via `CreateProcessWithTokenW` when needed) with `CREATE_SUSPENDED | CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP | EXTENDED_STARTUPINFO_PRESENT`, pseudo-console only when an interactive terminal is requested (v1: pipes only, no PTY), handle inheritance restricted via `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (only the three std pipe handles are inherited, nothing else).
4. Assign to the job before resuming the main thread, then `ResumeThread`.
5. Read stdout/stderr concurrently with bounded buffers (tokio `AsyncRead` over overlapped pipes), enforce deadline and cancel: on timeout or cancel, `TerminateJobObject` and report exit status `killed`.
6. Shell: PowerShell 7 (`pwsh`) discovered by absolute path (never PATH search for the shell itself), falling back to Windows PowerShell 5.1 at its absolute system path; invoked with `-NoProfile -NonInteractive -NoLogo` (execution policy is not a security boundary and is left at the user's setting); the command is passed with `-Command` from a UTF-8 file-less argument, quoted by a tested quoting function (`bh-sandbox::quote`), with `$ErrorActionPreference='Stop'` prefix. Arguments from the model for direct exec tools never go through a shell.
7. Same launcher for hooks, MCP stdio servers (MCP servers run in their own job with the same limits but a different env allowlist containing only explicitly configured variables) and any future code-running tool.

### 7.3 Command classification (not a boundary)

For approval UX and `Auto`: parse PowerShell via the PowerShell language parser (invoked as `pwsh -NoProfile -Command [System.Management.Automation.Language.Parser]::ParseInput(...)` inside the sandbox launcher, returning a JSON AST summary; timeouts 2 s; failure means "unknown" which means `Ask`). A command is `SafeReadOnly` only if every command element is on a built-in allowlist of read-only cmdlets/programs with checked argument shapes (`Get-ChildItem`, `Get-Content`, `Select-String`, `git status|diff|log|show` without `--ext-diff`/pager flags, `cargo check|metadata`, `rustc --version`, and so on), with no redirection to files, no pipelines into non-allowlisted commands, no subexpressions invoking unknown commands, no variable-expanded command names, no `&`/`.` call operators with computed targets. Everything else is `Exec` requiring policy. Classification is explicitly treated as best effort: its failure mode is an extra prompt, never a silent allow of something unparseable.

### 7.4 v2 roadmap (documented, not built)

AppContainer or a dedicated low-privilege local user for shell with per-project ACL grants; Windows Filtering Platform per-process outbound blocking (needs elevation, optional installer component) for true network confinement; Windows Sandbox / Hyper-V isolation for "untrusted repo" mode. The `Sandbox` trait in `bh-sandbox` (`spawn(SpawnSpec) -> Child`, `SpawnSpec` includes `network: NetworkPolicy` and `fs: FsPolicy`) is designed so these slot in; v1 implements `NetworkPolicy::Unrestricted` and `FsPolicy::UserLevel` only and returns `SandboxFailure` for unsupported requested policies instead of pretending.

## 8. Network egress and SSRF

- Egress inventory (complete list): provider APIs (api.anthropic.com, api.openai.com or configured gateway), `web_fetch` tool, MCP servers (their own), updater (signed releases only), shell commands (not confined in v1). No telemetry in v1. No other component opens sockets; no listening sockets exist.
- `web_fetch` (and media downloads, if any): schemes `https` (and `http` only via explicit user allow rule); reject userinfo URLs; resolve DNS ourselves, reject if any resolved IP is loopback, link-local (169.254/16, fe80::/10), private (10/8, 172.16/12, 192.168/16, fc00::/7), CGNAT (100.64/10), multicast, unspecified, or an IPv4-mapped form of those; connect to the validated IP (custom reqwest resolver pinning) with the original Host/SNI to defeat DNS rebinding; follow at most 5 redirects, re-validating each hop; response size cap 5 MiB, timeout 30 s; content converted to text/markdown by a sanitizer, scripts discarded; result is tainted `Untrusted`; each new host asks in `Ask`/`AcceptEdits`, allowed by user host rules in `Auto`; query strings are shown in the approval card so data-in-URL exfiltration is visible.
- Provider clients: TLS via rustls with the system and webpki roots, no custom CA unless configured by the user, HTTP/2, no proxy credentials logged, `base_url` must be https (loopback http allowed for local gateways) and is shown in settings.
- Outbound request bodies are built only from the projected conversation; no environment dumps or machine identifiers are ever added. The user agent is `BarryHarness/<version>` without OS details, except on the Claude and ChatGPT account sign-in paths, which send the `claude-cli` and `codex_cli_rs` user agents those OAuth clients expect (see the README).

## 9. Secret handling summary

Implemented in release 0.1.0:

- Stored credentials live only in the Windows Credential Manager through `keyring`; environment variables are the only other source.
- The `ApiKey` wrapper in `bh-provider`, the provider configurations and providers, and `bh_auth::Tokens` mask credentials in their `Debug` output, and every credential header is marked with `set_sensitive`; a credential that is not a valid header value fails with an authentication error instead of being replaced.
- Every HTTP client that carries credentials (provider adapters, the model list, token exchange and refresh) refuses redirects; token requests time out after 30 seconds.
- Error body excerpts from every provider adapter pass through a key-pattern redactor (`sk-ant-`, `sk-`, `AIza`, `ya29.`); the Anthropic adapter additionally replaces the exact key and its percent-encoded forms in error bodies and redirect targets.
- Credentials never travel in URLs: API keys and tokens go only in headers or token request bodies, and request errors are reported and logged without their URL.
- No OAuth client secret is embedded in the code; Google sign-in reads `BH_GEMINI_CLIENT_SECRET` at run time.

Planned:

- `SecretString` end to end for every credential.
- A log redaction layer plus a startup self-test that logs a canary and asserts it is scrubbed.
- Env scrubbing for children (7.1). MCP secrets: referenced from keyring by name, injected into the child env at spawn only.
- Secret scanner on tool output (section 3.5) and on text the user pastes.
- Diagnostics export contains versions, redacted config, error counts and logs (redacted), never message content, events or blobs unless the user ticks an explicit "include conversation" option for a specific session.
- Memory: keys zeroized after use where feasible (`zeroize`); acknowledged limitation that reqwest copies header bytes internally.

## 10. Auditing and rate limits

`audit_log` (storage.md 3.8) records security events; the UI shows it under Settings > Security with filter and export. Budgets enforced in `bh-agent` and surfaced as policy: max steps per turn (default 50), max tool calls per turn (default 200), per-turn and per-session token and cost ceilings (user-set; default soft warn at $5 per session, hard stop configurable), per-day media generation count and cost ceiling, max parallel tool concurrency 8. Hitting a budget raises `AgentEvent::Notice` and pauses for user confirmation rather than failing silently.

## 11. Dependencies and build hygiene

`cargo-deny` (licenses, bans, advisories, sources) runs in CI; `cargo-audit` is planned; `Cargo.lock` committed; unsafe code confined to `bh-sandbox` (Windows FFI via `windows` crate), `#![forbid(unsafe_code)]` in every other crate; clippy `-D warnings`; Tauri updater (if used) requires signature verification with a pinned public key; release builds use locked dependencies and a pinned toolchain and are published as an unsigned zip with a SHA-256 checksum (code signing is planned); frontend dependencies limited to the Rust crates (no npm runtime dependencies in the shipped bundle, removing the JS supply-chain surface).

## 12. Security test plan

Status: planned. None of the checks in this section ship in release 0.1.0; the repository contains no test suites or fixtures yet. The section records the verification the design calls for.

1. Path suite: table of hostile paths (`..\..\Windows`, `C:\Windows\System32`, `\\?\C:\`, `con.txt`, `file.txt::$DATA`, `PROGRA~1`, trailing-dot names, junction to outside, symlink to outside, case variants, mixed separators, very long paths) all classified `Outside` or rejected; junction created concurrently between check and open (race test) must not allow escape.
2. Policy suite: golden verdict tables per mode x capability x taint x rule combination; property test that adding a deny rule never turns Deny/Ask into Allow, and hooks never loosen.
3. Injection corpus: fixtures of injected pages/files (exfil via URL, instruction to run curl, instruction to edit `.git\hooks`) run against the policy engine with a scripted "hijacked model" asserting each action is denied or asks, in every mode including `Auto`.
